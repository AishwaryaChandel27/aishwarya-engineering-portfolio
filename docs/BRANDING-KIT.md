### Technical post 1 — Retrieval before generation
A useful document assistant needs more than a confident answer.

It needs to show where that answer came from—and recognize when the source does not contain enough information.

For my portfolio demo, I started smaller: editable source text, paragraph retrieval and exact passages with source numbers. There is no LLM behind this demo.

That makes the retrieval behavior easy to inspect before adding embeddings, generation or a paid API.

My next evaluation step would be a set of answerable and unanswerable questions, with expected source passages for each.

### Technical post 2 — A pipeline can finish and still be wrong
A successful run does not prove the data is correct.

I check three separate things:
• Completeness: did all expected records arrive?
• Correctness: did transformations produce the expected values?
• Reconciliation: can accepted and rejected records explain the input?

My portfolio fixture has five records. Two pass. Three are rejected with explicit reasons. The counts reconcile back to five.

It is a small example, but it shows why exception reporting belongs in the design from the start.

### Technical post 3 — A fallback is a product decision
While reviewing Vihaara’s AI integration, I traced the path from OpenAI to Gemini to predefined fallback content.

That path can keep an interface usable when providers fail. But users also need to know which kind of response they received.

A predefined fallback should not appear to be a fresh model-generated analysis.

The same applies to privacy: saving records locally does not mean an AI request stays on the device. The actual request path matters more than a reassuring label.

Clear states and accurate explanations are part of the engineering.

### Drowsiness detection
# Eye Aspect Ratio drowsiness prototype
Python webcam prototype using OpenCV, dlib facial landmarks, SciPy distances, Tkinter and pygame audio.

**Status:** Needs runtime fixes before reliable use. Not a certified driver safety system.

**Architecture:** Webcam → grayscale frame → facial landmarks → average eye ratio → threshold over consecutive frames → audio/visual alert.

**Setup:** Clone the public repository. Enter `Driver Drowsiness Detection`. Install OpenCV, dlib, imutils, pygame and scipy in a compatible Python environment; Tkinter may need the OS package. Provide the required 68-point landmark model at `models/shape_predictor_68_face_landmarks.dat` and the alert audio. The script is `Drowsiness_Detection.py`, not `main.py`.

**Known issues:** Initialize the global frame counter; repair camera lifecycle in the Stop handler; avoid blocking the Tkinter event loop; verify missing-model, no-camera and camera-disconnect behavior.

**Validation plan:** EAR helper fixtures; frame threshold boundary; counter reset; audio start/stop; safe camera cleanup; representative lighting, eyewear and camera positions. No accuracy is claimed without a documented labeled dataset and evaluation method.
